## 1. Межі версії v1.0

**Входить до версії v1.0:**
- Створення нового рецепта із зазначенням назви, списку інгредієнтів (назва, кількість, одиниця вимірювання) через вебінтерфейс.
- Перегляд довідника збережених рецептів.
- Складання розкладу меню на тиждень (призначення обраних рецептів на конкретний день тижня та прийом їжі) і його перегляд.
- Автоматична генерація списку покупок на основі складеного тижневого меню з підсумовуванням кількості однакових інгредієнтів.
- Зберігання рецептів та розкладу меню у реляційній СКБД MySQL.
- Експорт згенерованого списку покупок у вигляді текстового файлу.

**Не входить до версії:**
- Редагування та видалення існуючих рецептів.
- Редагування та видалення записів у розкладі меню.
- Авторизація та розподіл облікових записів користувачів.
- Підрахунок калорійності страв і облік домашніх запасів продуктів.
 

## 2. Функціональні вимоги

| ID | Вимога | Критерій приймання |
| :--- | :--- | :--- |
| **FR-01** | Система повинна дозволяти Користувачу створити новий рецепт, вказавши унікальну назву та перелік інгредієнтів (назва, кількість, одиниця вимірювання). | **AC-01:** Коректний рецепт зберігається в систему і відображається у довіднику рецептів. |
| **FR-02** | Система повинна відхиляти збереження рецепта, якщо його назва порожня, вже існує в довіднику, або якщо кількість будь-якого інгредієнта дорівнює чи менша за нуль. | **AC-02:** Рецепт із некоректними даними не зберігається; Користувач отримує повідомлення із причиною відхилення. |
| **FR-03** | Система повинна дозволяти Користувачу призначити наявний рецепт на обраний день тижня та прийом їжі. | **AC-03:** Після вибору дня, прийому їжі та існуючого рецепта запис додається до тижневого розкладу і показується в меню. |
| **FR-04** | Система повинна відхиляти додавання запису до розкладу меню, якщо обраний день тижня та прийом їжі вже зайнятий іншою стравою. | **AC-04:** Запис не додається до розкладу; Користувач отримує попередження про те, що обраний прийом їжі вже заплановано. |
| **FR-05** | Система повинна формувати єдиний список покупок для поточного тижневого розкладу, автоматично додаючи кількість інгредієнтів з однаковою назвою та одиницею вимірювання. | **AC-05:** Якщо два або більше рецептів містять однаковий інгредієнт, у згенерованому списку він відображається одним рядком із сумарною кількістю. |
| **FR-06** | Система повинна повідомляти Користувача про неможливість згенерувати список покупок, якщо розклад меню на тиждень порожній. | **AC-06:** За порожнього розкладу список не генерується, а виводиться попередження про необхідність додати страви до меню. |
| **FR-07** | Система повинна дозволяти Користувачу експорт згенерованого списку покупок у вигляді текстового файлу. | **AC-07:** При виборі дії збереження браузер завантажує непорожній текстовий файл із переліком покупок. |


## 3. Нефункціональні вимоги

| ID | Вимога | Критерій приймання |
| :--- | :--- | :--- |
| **NFR-01** | **Постійність даних:** Усі створені Користувачем рецепти, інгредієнти та записи розкладу повинні постійно зберігатися у реляційній базі даних MySQL. | **AC-NFR-01:** Після зупинки та повторного запуску вебсервера раніше внесені дані успішно завантажуються з БД без втрат. |
| **NFR-02** | **Точність обчислень:** Зберігання в базі та підсумовування кількості інгредієнтів має виконуватися без втрати точності для дробових чисел (наприклад, 0.25 кг + 0.5 кг = 0.75 кг). | **AC-NFR-02:** Автоматичні тести з дробовими значеннями проходять зі 100% точністю без похибок округлення. |
| **NFR-03** | **Стійкість до помилок введення:** Застосунок не повинен завершувати роботу аварійно у разі введення Користувачем некоректних або неповних даних у форми. | **AC-NFR-03:** При некоректних вхідних даних сервер повертає інформативний текст на сторінці, а не системну сторінку помилки. |
