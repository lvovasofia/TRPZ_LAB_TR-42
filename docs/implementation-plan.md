# План реалізації версії v1.0


## Залежності між компонентами

| Компонент | Залежить від | Звідки видно |
| :--- | :--- | :--- |
| User (реєстрація, вхід) | нічого | Class Diagram: User не залежить від інших класів |
| Recipe, Ingredient | User | Recipe належить User; Ingredient існує лише в Recipe |
| WeeklySchedule, ScheduleEntry | User, Recipe | ScheduleEntry посилається на Recipe; розклад належить User |
| ShoppingList, ShoppingListItem | WeeklySchedule, Recipe, Ingredient | ShoppingList формується з розкладу й підсумовує інгредієнти |

## Послідовність реалізації

### Етап 1. Основа та користувачі

Підключаємо сховище даних, щоб дані зберігалися між перезапусками (NFR-01). Реалізуємо реєстрацію та вхід (UC-01, UC-02; FR-01…FR-04). Пароль зберігаємо у вигляді хеша (NFR-04).

Перевірка: критерії AC-01…AC-04; у сховищі немає паролів у відкритому вигляді; користувач бачить лише власні дані.

### Етап 2. Рецепти

Реалізуємо створення рецепта з інгредієнтами та перевірки назви й кількості (UC-03; FR-05, FR-06), а також перегляд довідника (UC-04; FR-07). Кількість зберігаємо як `Decimal` (NFR-02).

Етап іде після першого, бо рецепт належить користувачу. Функцію підсумовування інгредієнтів за назвою та одиницею (основа FR-11) можна написати й протестувати вже тут, бо вона не залежить від бази й інтерфейсу.

Перевірка: критерії AC-05…AC-07; спроби зберегти рецепт із порожньою чи дубльованою назвою та з кількістю ≤ 0.

### Етап 3. Тижневий розклад

Реалізуємо складання розкладу з перевіркою зайнятого слота (UC-05; FR-08, FR-09) і перегляд тижневого розкладу (UC-06; FR-10).

Етап іде після другого, бо запис розкладу посилається на наявний рецепт.

Перевірка: критерії AC-08…AC-10; спроба додати другу страву в уже зайнятий день і прийом їжі; відображення порожніх комірок.

### Етап 4. Список покупок

Підключаємо підсумовування до розкладу й реалізуємо генерацію списку (UC-07; FR-11) та повідомлення для порожнього розкладу (FR-12).

Етап іде останнім серед функцій, бо список формується з розкладу та рецептів.

Перевірка: критерії AC-11, AC-12; розклад із двома рецептами з однаковим інгредієнтом; порожній розклад.

### Етап 5. Інтеграція та нефункціональні вимоги

Проходимо наскрізний сценарій: реєстрація → рецепти → розклад → список покупок. Окремо перевіряємо нефункціональні вимоги.

## План перевірки нефункціональних вимог

| Вимога | Спосіб перевірки | Етап |
| :--- | :--- | :--- |
| NFR-01 | Зупинити й повторно запустити систему, перевірити наявність раніше внесених даних (AC-NFR-01) | 1, 5 |
| NFR-02 | Автоматичні тести: 0.25 кг + 0.5 кг = 0.75 кг; 0.125 кг + 0.375 кг = 0.5 кг; інгредієнти з різними одиницями не об'єднуються; регістр назви не впливає на об'єднання (AC-NFR-02, AC-11) | 2, 4 |
| NFR-03 | Набір некоректних вводів: порожні поля, текст замість числа, від'ємні значення, дуже довгі рядки (AC-NFR-03) | 5 |
| NFR-04 | Переглянути сховище: у записі користувача лише хеш пароля (AC-NFR-04) | 1 |

## Інтеграція змін

Кожен етап реалізується в окремій гілці й потрапляє в `main` через Pull Request. Перед злиттям його переглядає інший учасник команди. PR приймається, якщо збірка й тести проходять, а для цієї частини виконані критерії приймання з матриці простежуваності.
